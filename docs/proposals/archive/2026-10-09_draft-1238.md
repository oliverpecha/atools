## 1. Graph Topology, Visual Semantics & Workspace Isolation



### 1.1 Single Source of Truth & Generated Views



* **Canonical Source (`graph.toml`):** One primary persona graph serves as the central representation, while Views `02` (Swimlane Sequence), `03` (Context and Session Views), and `04` (Guard Map) are retained as generated views derived from the same `graph.toml` definition. The Guard Map functions as an annotation layer over the persona graph rather than an independent topology.


* **Primary Deliverable:** Raw `.mmd` Mermaid definitions are the canonical visual artifacts (rendered at full resolution via `mermaid-cli` or native Markdown viewers rather than auto-layout PNG thumbnails).


* **Current Morphology:** The workflow operates as a deterministic spine (`gate`) orchestrating bounded loops (adversarial oracle qualification, implementation retries, escalation resolution, and closeout archivation).


* **Escalation edges in the graph:** `gate → Architect` (never drawn through the Implementer) carries the `Escalation record` for `retries_oracle_exhausted`, `retries_implementer_exhausted`, `hard_cap_exhausted`, and `blocked`. A secondary `gate → Owner` control edge activates when the Architect escalates to the human Owner, fails/times out, on `retries_archivist_exhausted`, or when `escalation_policy()` targets the Owner directly.



### 1.2 Orthogonal Edge Semantics



Every edge in the graph is classified along two independent axes: **acceptance verification** (line style) and **routing role** (color or arrowhead).

### 1.3 Module-by-Module Context & Piping Blueprint



At runtime, all artifacts reside on disk and `gate` routes file pointers to each session. Saying "`gate` never interprets prose" means `gate`'s routing logic branches strictly on deterministic schema fields (enums, booleans, hashes, exit codes, counters), never on free-text strings. To prevent context rot from dead-end debugging turns while preserving end-to-end architectural intent, context lifecycles and OS UIDs are strictly partitioned:

| Module | OS UID & Context Strategy | Technical Piping & Execution Blueprint |
| --- | --- | --- |
| **`gate` (Unified Control Spine & Verifier)** | **UID `gate` / Deterministic State File (`state.json`)** | Single binary (`orchestrator` + `dispatcher` + `verifier`) running as an event-driven CLI/daemon. Communicates with the human Owner via a **Notification Adapter** (interactive terminal prompt when attached; Telegram/webhook message when detached). Whenever a human decision is required, `gate` writes `status: "hold"` to `state.json`, emits the notification (`escalation_alerts_sent++`), and exits cleanly. The Owner resumes execution via CLI (`gate resolve <sprint> ...`) or an authenticated webhook/bot reply that writes the decision `resolution` and re-invokes `gate`.

### 1.4 Every Place the Workflow Reaches the Owner



1. **Phase 1 Intent Q&A (§3.2, §4.1):** Interactive `Owner ↔ Architect` conversation to establish requirements and name the sprint (`YYYY-MM-DD_<slug>`) before `spec-v1.md` is authored.


2. **Escalation Resolution (§5.2, §5.4, §6.3):** When the Architect cannot resolve an escalation without changing product intent, when `mutant_waiver_authority: owner`, when `retries_archivist_exhausted` fires, or when `escalation_policy()` routes directly to the Owner.


3. **Live Run Execution & Gated Approvals (§4.3, §5.5):** When `approval_live_run: owner` is active, for Phase 4 Archivation Plan review and sign-off (mandatory `approval_archivation_plan: owner`), and for executing the Live Run inside the Owner's credentialed environment.


4. **Closeout & Merge (§3.2, §5.5):** Reviewing `diff-risk-review.md` (including any waived mutant disclosures), selecting items from `backlog-proposal.md` for the repo backlog, and executing the final `git push`.



### 1.5 Multi-Sprint Directory Architecture & 4-UID OS-Level Isolation



To enforce **`P` (Private Artifacts Unreadable)** mechanically, neutralize context-poisoning blast radii across phases, and scale cleanly across hundreds of sprints, the workspace is partitioned across **four Linux OS accounts (`gate`, `plan`, `impl`, `ship`)** with standalone local git clones (`workspaces/`) and a UID-partitioned POSIX IPC mailbox (`handoff/`):

* **`gate`:** Runs the deterministic `gate` binary only. Owns `gate-repo/` and `repos/target-repo/` (`chmod 700`). Zero LLM sessions ever execute under `gate`.


* **`plan`:** Runs Phase 1–2 planning & adversarial verification LLM sessions (`Architect`, `Challenger`).


* **`impl`:** Runs Phase 3 untrusted code execution (`Implementer`).


* **`ship`:** Runs Phase 4 closeout curation (`Archivist`), isolated so poisoned repository diffs or implementer notes cannot bleed backward into `plan` or `gate`.

### 1.6 Resolution of Formerly Unguarded Edges



1. **Implementer → `gate` (Session Closure & Pre-Check Guards):** Guarded mechanically (**solid line**) *before* any Offline Run executes.


* **Gate Pre-Flight Integrity Check:** `gate` (`verifier`) first verifies that the frozen `oracles/vN/` directory inside `gate-repo/` matches the immutable hash in `contract-vN.json`. A mismatch halts the runner immediately as a system integrity error (never consuming an Implementer retry).


* **Closure & Code Guards:** `gate` validates that `closure-NN.json` conforms to schema (`reason: done | blocked`, nullable `proof_id`, `notes`, `backlog`, plus `min_attempts_before_block` and—when `solution_key_exposure: full`—`solution_key_divergence` for `reason: blocked`), fetches branch `wip/attempt-N` from `workspaces/wip-attempt-N/` into `workspaces/gate-verify/`, and checks `git diff BASE..HEAD` against `ALLOW`/`FROZEN` scope (`scope.txt`), credential/secret leak scan, and forbidden-call lint. If any closure guard fails, `gate` emits a red `runs/ev-NN.json` citing the violated guard and routes it identically to a failed Offline Run (consuming 1 `retries_implementer` attempt and passing the guard failure in `prior_attempt.json`).




2. **Archivation Plan Hand-off (Split into Two Explicit Edges):** Because the `Archivation plan` undergoes both mechanical policy verification and semantic review, it is modeled as two separate edges:


* **Edge 1 — `Archivist → gate` (Solid Line / Script-Accepted):** `gate` enforces the precondition that `diff-risk-review.md`, `backlog-proposal.md`, `commit-plan.sh`, and `plan/` exist and parse. `gate` (`verifier`) runs the deterministic regex policy check on `commit-plan.sh` and `plan/*.msg` (subject format, required git trailers, no forbidden paths, matching `.patch`/`.msg` pairs, and a mandatory `Waived Mutants & Residual Risk` section in `diff-risk-review.md` if any mutant was waived), **ephemerally executes feature commits `01 .. N-1` from `commit-plan.sh` in `workspaces/gate-verify/` to verify 100% bit-for-bit git tree-equality against the pinned contract-hash git tag across all paths (`git diff <contract-tag> HEAD` is empty, with zero path exclusions), applies the final test-graduation commit (`NN-graduate-tests.patch`) and verifies it touches only `test/**` with strictly additive changes (`git diff --diff-filter=MD` is empty), and runs the repo's `Test` suite to confirm all existing and newly graduated tests pass**.


* **Edge 2 — `gate → Owner` (Dashed Line / Human-Accepted):** Once Edge 1 passes, `gate` sets `status: "hold"` in `state.json` and hands off the validated `Archivation plan` strictly to the human Owner (`approval_archivation_plan: owner`) for semantic review of `diff-risk-review.md`, `commit-plan.sh`, and `backlog-proposal.md`. Automated rejections occur only on Edge 1 (`gate` verifier checks bounded by `retries_archivist`, escalating to the `Owner` on `retries_archivist_exhausted`). Human `Owner` revision requests on Edge 2 bypass budget limits entirely and re-invoke the Archivist with the Owner's specific change notes.

## 4. Standardized Artifact & Package Schemas



**Naming & Lifecycle Rules:**

* **Records** are structured data files emitted by an agent or `gate`.


* **Plans / Scripts** are actionable bundles reviewed and executed during closeout.


* **Single Ownership of `solution_key.patch`:** Authored solely by the Architect in Phase 1 (and updated only by the Architect if Phase 2 qualification exposes a bug or spec refinement), audited by the Challenger, verified against Step 1 closure guards and Stage 2b repo `Test` in `qual.json`, and copied into `oracles/vN/` when frozen so its canonical hash is locked at Oracle freeze.

## 5. Lifecycle Mechanics & Loop Governance



### 5.1 State Persistence, Epoch-Immutable Contract & Idempotent Transitions (`gate`)



* **External State File (`specs/<sprint>/runs/state.json`) vs. Epoch-Immutable `contract-vN.json`:** `gate` (`orchestrator`) initializes `state.json` at the start of Phase 1 (scoped to `run_id` across any `Spec vN` revisions) to track runtime counters (`retries_oracle`, `retries_implementer`, `retries_archivist`, active stage, `active_contract`, `status`, and any dynamic retry increments granted during escalations). `contract-v1.json` is minted **once** at Oracle `v1` freeze (entering Phase 3) and is never mutated:


* If additional retries are granted on escalation without changing the spec or oracle, `state.json` and `escalation-NN.json` (`resolution`) are updated while `contract-v1.json` remains static.


* If an escalation updates `spec-vN.md`, `scope.txt`, or `oracles/vN/`, `gate` freezes the updated Oracle and mints `contract-vN+1.json` to start a new contract epoch.


* If `state.json` is lost or corrupted, all counters, active contract epochs, and grants can be deterministically reconstructed from `runs/ev-*.json`, `escalation-NN.json` (via `resolution.retries_granted` and `resolution.new_contract`), and the extended `sessions.tsv` ledger (`model`, `turns`, `tokens`, `cost`, `accepted_items`, retry counters, `escalation_alerts_sent`).




* **Idempotent Write-Ahead Transitions:** Every state transition is idempotent, keyed by `(run_id, transition_id, attempt)` (and including `contract_hash` from Phase 3 onward), and writes a `"started"` marker to `state.json` *before* launching a process or sending an alert.


* If `gate` crashes after launching an agent session, a restarted `gate` detects the `"started"` marker and does not launch a duplicate session or double-spend the budget.


* Similarly, during an Owner `hold` wait, idempotency prevents sending duplicate escalation alerts.





### 5.2 Adversarial Oracle Qualification Loop (`Architect ↔ gate ↔ Challenger`)



1. **Adversarial Authoring & Mechanical Qualification:**

* **Architect Spec & Reference Key:** In Phase 1, following interactive Q&A with the Owner, the Architect (`sudo -u plan`) authors `spec-v1.md` and `solution_key.patch`.


* **Challenger Audit & Oracle Authoring:** In Phase 2, the cross-family Challenger (`sudo -u plan`) audits `spec-v1.md` and `solution_key.patch` for semantic flaws (missing requirement coverage, shared misreadings, weak assertions such as checking `has("email")|not` when an email leaks under a renamed key `contact`) and authors `oracles/v1/` (`proofs/`, `probe.sh`, `mutants/`, `scope.txt`, `coverage.md`).


* **Mechanical Qualification (`qual.json`):** `gate` (`verifier`) runs `oracles/v1/` in `workspaces/gate-verify/`, verifying that:


1. The null base implementation fails `proofs/` (`null_base: red`),


2. `solution_key.patch` passes Step 1 Closure Guards (`scope.txt`, secret scan, forbidden-call lint) (`solution_key_guards: green`),


3. `solution_key.patch` passes `proofs/` and `probe.sh` repeatedly (`solution_key_green: 3/3`),


4. `solution_key.patch` passes Stage 2b (the target repo's existing `Test` suite) (`solution_key_repo_test: green`), and


5. All `mutants/*.patch` are killed (`killed: true`, exit `1`).






2. **Four-Layer Defense Against Weak Proofs:**

* *Value-level sentinel proofs:* Seed known sentinel strings (e.g., a test email) and fail if the literal string appears anywhere in the raw response payload.


* *End-to-end probe (`probe.sh`):* Inspects actual runtime outputs and performs independent recomputation.


* *Adversarial mutants:* Challenger supplies sabotaged patches (`mutants/contact_leak.patch`) that expose weak assertions and remain archived in `oracles/vN/mutants/` for future verification.


* *Visible residual risk & Owner disclosure:* Any surviving mutant (`killed: false`) waived at escalation (recorded in `escalation-NN.json` `resolution.waived_mutants`) is stamped as a dedicated `mutant/<name>.patch | waived | escalation-NN` row in `checklist.md` and must be explained in `diff-risk-review.md` for Owner review at closeout.




3. **Deterministic Convergence & `retries_oracle_exhausted` Resolution:**

* **Immediate Freeze on Green `qual.json`:** If `qual.json` passes completely (`null_base: red`, `solution_key_guards: green`, `solution_key_green: 3/3`, `solution_key_repo_test: green`, all mutants `killed: true`), `gate` freezes the Oracle immediately (locking the canonical hash of `solution_key.patch`) and mints `contract-v1.json`.


* **Refinement Iterations (`v2`, `v3`):** If `qual.json` is red (e.g., a Challenger proof exposed a flaw in `solution_key.patch`, `solution_key.patch` violated `scope.txt` or broke an existing test in `test/`, an over-strict proof rejected a valid `solution_key.patch`, or a mutant survived with `killed: false`), `gate` wakes the Architect/Challenger to resolve the discrepancy (updating `spec-vN.md`/`solution_key.patch` or producing `oracles/vN/` directly), bounded by `retries_oracle`.


* **When `retries_oracle` Runs Out (`trigger: retries_oracle_exhausted`):** `gate` assembles `escalation-NN.json` (with `oracle_review` populated from `qual.json`) and routes it via `gate → Architect` (or `gate → Owner` if `mutant_waiver_authority: owner`). The authority records its decision in `escalation-NN.json` (`resolution`), choosing one of three actions:


1. Grant additional `retries_oracle` budget in `state.json` (`action: "grant_retries"`).


2. Write the next oracle version (`oracles/vN/`) directly (`action: "update_oracle"`, re-verified by `qual.json`).


3. Waive the surviving mutant(s) (`action: "waive_mutant"`, governed by `mutant_waiver_authority: architect | owner`, default `architect`): the latest oracle freezes and proceeds to Phase 3, appending `mutant/<name>.patch | waived | escalation-NN (sha256: ...)` rows in `checklist.md`.







### 5.3 Coverage Map & Checklist Stamping Rule



* `coverage.md` explicitly lists every proof ID (plus `probe.sh`) required to satisfy each requirement (`R_i → [proof_a, proof_b, ..., probe.sh]`).


* `specs/<sprint>/checklist.md` tracks `Offline Run` and `Live Run` receipts in separate columns:


* When `live_run: none`, the `Live Run` column is initialized to `n/a`, and `gate` stamps each `R_i` row `Status: done` once all mapped `proofs/`, `probe.sh`, and the target repo's `Test` suite exit `0` (`green`) in the composite `Offline Run` receipt (`ev-NN.json`) against the **exact same `head` commit SHA** (pinned by the contract-hash git tag).


* When `live_run: required`, `Status` remains `open` after the `Offline Run` column is populated and only flips to `done` when the `Live Run` column also records `0` (`green`) receipts for all mapped `proofs/` and `probe.sh` on the **identical `head` commit SHA**.


* Surviving mutants waived in Phase 2 occupy their own `mutant/<name>.patch | waived | escalation-NN` rows and **never** mark a requirement row (`R_i`) as `done` or `waived`.


* Closeout requires **zero `open` requirement rows** in `checklist.md` (every `R_i` row must be `done`, and any waived mutant rows must be disclosed in `diff-risk-review.md`).





### 5.4 Implementation Routing, Retries & Blocked Escalations (Settled)



1. **Standalone Clone & Retry / Restart Mechanics:** For each attempt $N$, `gate` (`dispatcher`) creates a fresh standalone local clone (`git clone --local --no-hardlinks repos/target-repo workspaces/wip-attempt-N`, owned by `impl:impl`, `chmod 700`) checked out at `BASE` on branch `wip/attempt-N`, and launches a fresh Implementer session (`sudo -u impl`, frontloading static prefixes + `solution_key.patch` when `full`). The Implementer is instructed to commit her work incrementally onto `wip/attempt-N` for full traceability. When the Implementer writes `closure-NN.json`, `gate` (`verifier`) fetches `wip/attempt-N` into `workspaces/gate-verify/` to evaluate closure guards and the Offline Run. When a Gate closure guard or Offline run is red and `retries_implementer` budget remains, `gate` deletes `workspaces/wip-attempt-N/`, creates a clean standalone clone `workspaces/wip-attempt-N+1/` at `BASE`, and writes `prior_attempt.json` (previous diff patch, `failing_step` and `failing_line` from the last `ev-NN.json`, and attempt count) to `handoff/<sprint>/work-order/` strictly as an optional hint. `log_tail` from Escalation records goes to the Architect only and is never forwarded to a later Implementer.


2. **Deterministic Routing on Closure `reason`:**

* `reason: done` → Triggers `gate` **Step 1 Pre-Flight & Closure Guards** followed immediately by the **Step 2 Fail-Fast Offline Run**.


* `reason: blocked` *(Consolidates former `blocked` and `dispute`)* → Implementer halts when it cannot satisfy the Gate due to an `ALLOW` scope restriction, missing architectural decision, or suspected over-constrained proof (`proof_id` may be `null` on scope/architectural blocks).


* **Anti-Early-Give-Up Guards:** `gate` mechanically rejects `reason: blocked` (treating an invalid `blocked` claim as a failed attempt that consumes 1 `retries_implementer` credit) unless:


1. `attempts >= min_attempts_before_block`,


2. all Step 1 mechanical `ALLOW`/secret/lint closure guards pass and the target repository's own compilation and `Test` suite pass in the offline sandbox (unless a failing test in `Test` is the exact blocker cited in `detail`), and


3. **when `solution_key_exposure: full**`, `closure-NN.json` includes a non-empty `solution_key_divergence` explaining why `solution_key.patch` could not be applied or adapted to pass the failing proof.




* **Escalation Routing:** Once those preconditions are met, `gate` assembles `escalation-NN.json` (`trigger: blocked`, citing `last_closure` and `evidence`) and routes it via `gate → Architect`. The Architect inspects `escalation-NN.json` in its persistent thread and records `resolution` in `escalation-NN.json`: either (a) updates `scope.txt` / `Spec vN` / `Oracle vN` (re-qualified via `qual.json`, minting `contract-vN+1.json` for a new contract epoch), (b) rejects the block and grants additional `retries_implementer` budget in `state.json`, or (c) escalates to the human `Owner` via `gate → Owner` (`status: "hold"`) if product intent must change.


* *Intra-Session Hard-Cap Termination (`trigger: hard_cap_exhausted`):* If a session is killed by the wall-clock supervisor (`timeout -k 15s`) or turn/token/cost hard caps, `gate` synthesizes `escalation-NN.json` (`trigger: hard_cap_exhausted`) from `state.json` and routes it via `gate → Architect`.





### 5.5 Closure Guards, Fail-Fast Offline Run, Live Run & Archivation Sequence (Settled)



1. **Step 1 — Gate Pre-Flight & Self-Tested Mechanical Closure Guards (Before Offline Run):**

* **Oracle Pre-Flight Hash Check:** `gate` (`verifier`) verifies `gate-repo/specs/<sprint>/oracles/vN/` against `contract-vN.json` (halting on corruption without consuming an Implementer retry).


* **Closure Guards:** Upon `Implementer → gate` closure, and *before* executing untrusted Implementer code, `gate` validates `closure-NN.json`, fetches `wip/attempt-N` into `workspaces/gate-verify/`, checks `git diff BASE..HEAD` against `ALLOW`/`FROZEN` scope (`scope.txt`), runs the credential/secret leak scan, and runs the forbidden-call lint.


* **Mandatory Self-Tests:** Every guard/scanner must pass its own built-in self-test (verifying it catches known synthetic leaks and forbidden calls) before evaluating the worktree so a broken lint cannot silently pass under `approval_live_run: auto`.




2. **Step 2 — Fail-Fast Offline Run (`proofs/` First, Repo `Test` Second):**


Once Step 1 guards are green, `gate` checks out the candidate commit in `workspaces/gate-verify/` with credentials blanked:


* **Stage 2a (Fast Feature Check):** Executes the Oracle's `proofs/*.sh` and `probe.sh` first so feature errors fail fast within seconds.


* **Stage 2b (Regression Armor):** Immediately executes the target repository's existing `Test` suite (`test/`) to guarantee zero regressions against prior specs.


* When both Stage 2a and Stage 2b exit `0`, `gate` writes the composite green `runs/ev-NN.json` (`steps[]`) and stamps the `Offline Run` column in `checklist.md`.




3. **Step 3 — Live Run (Before Archivist):** Governed by `live_run: none | required` and `approval_live_run: auto | architect | owner`. **`approval_live_run: auto` means the Owner pre-authorized the live run in `contract-vN.json`, and the live run still executes strictly within the Owner's environment/account (where real credentials reside), never under the `impl` user**; `gate` itself never holds or stores real keys. When green, `gate` stamps the `Live Run` column and marks requirement rows `Status: done` in `checklist.md`.


4. **Step 4 — Archivist Curation & Proof-to-Test Graduation:**

* Once Steps 1–3 are green and zero `open` rows remain in `checklist.md`, `gate` pins the approved state via an internal git tag in `repos/target-repo/.git` **keyed by `contract-vN.json` hash**, stages `spec-vN.md`, `approved.diff`, `oracles/vN/proofs/*.sh`, and `context.json` (`notes[]`, `backlog[]`, and `waived_mutants[]` from `escalation-NN.json`) into `handoff/<sprint>/ship-inputs/` (`chmod 750`, `gate:ship`), initializes standalone clone `workspaces/ship-worktree/` at `<contract-tag>`, and invokes the Archivist (`sudo -u ship`).


* The Archivist consumes `ship-inputs/` to author `diff-risk-review.md` (including a mandatory `Waived Mutants & Residual Risk` section if any mutant was waived) and craft commit messages in `plan/*.msg`.


* The Archivist merges the Implementer's `backlog` items with its own candidates into `backlog-proposal.md` (containing `none` if empty).


* **Proof-to-Test Graduation:** The Archivist translates the black-box `proofs/*.sh` into native repository tests inside `test/` as a dedicated final commit (`plan/NN-graduate-tests.patch` + `.msg`, restricted to `ALLOW: test/**`) in `commit-plan.sh`.




5. **Step 5 — Closeout Policy, 100% Feature Tree-Equality & Additive `Test` Check, Approval & Owner Push:**

* **Solid Edge (`Archivist → gate`):** `gate` verifies all required files exist in `handoff/<sprint>/archivation-plan/`, runs the regex policy check on `commit-plan.sh`, `plan/*.msg`, and `diff-risk-review.md`, **ephemerally applies feature commits `01 .. N-1` in `workspaces/gate-verify/` and verifies 100% bit-for-bit git tree-equality between the resulting tree and `<contract-tag>` across all paths (`git diff <contract-tag> HEAD` is empty, zero path exclusions), applies commit `N` (`NN-graduate-tests.patch`) and verifies it modifies only `test/**` and is strictly additive (`git diff --diff-filter=MD` is empty), and runs the repo's `Test` suite to prove all existing and newly graduated tests pass**.


* **Dashed Edge (`gate → Owner`):** Governed strictly by `approval_archivation_plan: owner` (`architect` and `auto` approval are retired). Once Edge 1 mechanical checks pass, `gate` marks `status: "hold"` in `state.json` and notifies the Owner via the Notification Adapter. If Edge 1 fails, `gate` loops back to the Archivist bounded by `retries_archivist` (escalating to the `Owner` on `retries_archivist_exhausted`). If the Owner requests changes on Edge 2, revisions loop back to the Archivist uncapped by budget counters.


* **Final Commit, Backlog Storage & Push:** Once approved, `gate` applies the verified commit chain (feature commits + graduated `test/` commit) to `repos/target-repo/`, commits the final stamped `specs/<sprint>/checklist.md` to `gate-repo` (`runs/ev-*.json` remain untracked), presents `backlog-proposal.md` items for the **Owner** to curate into the repo backlog, and the human **Owner pushes** to remote trunk.

## 6. Dynamic Budget & Escalation Functions



### 6.1 Intra-Session Hard Caps (`hard_cap`) vs. Inter-Session Loop Counters (`retries_*`)



Resource and iteration ceilings are partitioned into two distinct classes resolved at Phase 1 start into `state.json` and locked into `contract-vN.json` at Phase 3 Oracle freeze:

```text
effective_limit(dimension, contract_or_state, context) -> (limit, mechanism, on_exceed)

```

1. **Intra-Session Hard Caps (`hard_cap` → triggers `hard_cap_exhausted`):**

* Govern a **single CLI invocation**: `wall_clock` (`timeout -k 15s <limit>`), `turns`, `tool_calls`, `tokens`, and `cost_usd`.


* **Fail-Closed Adapter Guard:** If a contract specifies a hard cap dimension and the CLI adapter cannot confirm that the enforcement mechanism or CLI flag took effect, **the run refuses to start**.


* **Sub-Agent Spawner Prohibition:** Every CLI adapter mechanically disables native in-process sub-agent tools (`AgentTool` / sub-task spawners) so no persona can spawn an in-process child agent inside the same UID. Every persona transition must return to `gate`.


* **Universal Wall-Clock Supervisor:** Every CLI engine retains the external `sudo -u {plan|impl|ship} timeout -k 15s <limit>` wrapper as the hard wall-clock kill switch.




2. **Inter-Session Loop Counters (`retries_<stage>` → triggers `retries_<stage>_exhausted`):**

* Govern multi-session state machine loops tracked in `state.json`:


* `retries_oracle` → `retries_oracle_exhausted` (Phase 2 `Architect ↔ gate ↔ Challenger` qualification loop).


* `retries_implementer` → `retries_implementer_exhausted` (Phase 3 `Implementer ↔ gate` implementation loop, paired with `min_attempts_before_block`).


* `retries_archivist` → `retries_archivist_exhausted` (Phase 4 automated Gate mechanical rejections on Edge 1; human Owner revisions on Edge 2 are uncapped).

### 6.3 Dynamic Escalation Policy Function



Escalation routing resolves dynamically across all four phases (reading `state.json` in Phases 1–2 and `contract-vN.json` + `state.json` in Phases 3–4):

```text
escalation_policy(event, contract_or_state, context) -> decision (logged with inputs)

```

* **Inputs:** Event type (`retries_oracle_exhausted`, `retries_implementer_exhausted`, `retries_archivist_exhausted`, `hard_cap_exhausted`, `blocked`), risk tier, `mutant_waiver_authority`, time of day, and Owner availability.


* **Two-Tier Routing (`gate → Architect` then `gate → Owner`):** By default, `gate` routes `retries_oracle_exhausted`, `retries_implementer_exhausted`, `hard_cap_exhausted`, and `blocked` to the **Architect** first. `gate` routes directly to the human **Owner** (via the Notification Adapter) when:


1. The Architect explicitly escalates an unresolved spec/scope/mutant decision to the Owner (`resolution.action: "escalate_owner"`),


2. The synchronous Architect session itself fails or hits `hard_cap_exhausted`,


3. `retries_archivist_exhausted` triggers in Phase 4, or


4. `escalation_policy()` requires direct Owner authority (e.g., `mutant_waiver_authority: owner` or high risk tier).




* **Safe Default on No Response (`hold`):** Availability windows, time-of-day routing, and `escalation_alerts_sent` apply strictly when targeting the human **Owner**. If an Owner escalation receives no response within the availability window (or if a synchronous Architect invocation fails), the mandatory safe default is **`hold` (write `status: "hold"` in `state.json` and await human Owner intervention)—never auto-approve**.


* **Hold scope:** `hold` applies strictly to the actionable party's decision; an unanswered informational Owner notification never blocks a run that the Architect is authorized to resolve.
